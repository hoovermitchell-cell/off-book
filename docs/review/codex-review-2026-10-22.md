- P2 | `src/chess/stockfish-worker.ts:15` | A Worker script/WASM load error never rejects `engine.ready()`, so the screen stays on “Loading the engines…” and the UI's initialization error handler never runs. Connect Worker errors and a readiness timeout to promise rejection, and terminate the failed worker; propagate later failures to pending searches too.
- P2 | `src/drill/drill.ts:203` and `src/ui/drill-view.ts:309` | If Maia inference rejects during a game, `play()` rejects with phase still `black`, no legal destinations, and no visible error; the UI discards the rejected promise. An injected failure reproduced this after d4. Catch engine/inference failures, settle into a recoverable state with visible retry/restart guidance, and keep the round guard on recovery.
- P2 | `src/ui/drill-view.ts:334` | Typed underpromotions lose `m.promotion` when forwarded through `play(from, to)`; the drill defaults to a queen. For `7k/P7/8/8/8/8/8/7K w - - 0 1`, entering `a8=N` instead plays `a8=Q+`. Pass the parsed promotion through the UI helper to `drill.play()`.
- P2 | `src/drill/drill.ts:294` | Resign while a wrong prep move is being evaluated: the game-over event renders the played move, but the pending evaluation later undoes it before checking `isOver()`, without emitting a new render event. A deferred-engine probe changed history from `[e4]` to `[]` after resignation. Check the terminal state before mutating the board, or undo before emitting game-over and render that settled state.
- P2 | `src/ui/drill-view.ts:116` and `src/ui/drill-view.ts:256` | Two open tabs save their own stale progress snapshots. After A learns one position and B learns another, B's save removes A's learned position and loses its tally increment. Synchronize progress mutations across tabs and apply additions/increments to the latest saved state under serialized writes.
- P2 | `src/ui/drill-view.ts:116` and `src/ui/drill-view.ts:257` | Blocked or full local storage makes `save()` return false, but both callers ignore it and continue showing learned moves and earned tallies as usual; those gains disappear on reload without warning. Check the return value and show a persistent notice that progress is only available for this session.
- P2 | `src/ui/drill-view.ts:232` | Keyboard submission disables the focused move input while Black thinks. Re-enabling it never restores focus, so the next move cannot be typed without navigating back to the field; New game also leaves focus on a button that becomes hidden. Restore input focus when the student's turn returns if keyboard entry initiated the cycle, and after an explicit New game action, without taking focus from other controls.
- P2 | `src/ui/drill-view.ts:157` and `src/ui/app.css:84` | Prep moves in the scoresheet are identified only by a highlighter background; their markup carries no text or symbol identifying them as prep. Readers who cannot distinguish that fill lose the prep boundary, contrary to DESIGN.md's “never color alone” rule. Add a visible non-color marker and accessible text for prep moves or their boundary.
- P2 | `src/ui/drill-view.ts:186` | The explanation treats every 1.0 evaluation drop as a roughly 50% swing in winning chances. A position score and a score difference are different quantities; a fall from +5 to +4 does not imply that swing. Remove the fixed probability conversion and describe the score loss itself. The [Stockfish FAQ](https://official-stockfish.github.io/docs/stockfish-wiki/Stockfish-FAQ.html#interpretation-of-the-stockfish-evaluation) explains the nonlinear, engine-self-play probability model.
- P2 | `src/ui/drill-view.ts:198` | “Looked N moves ahead” presents UCI depth as full moves and a guaranteed search horizon, overstating the evidence in “How did it know?”. Label it as reported search depth in half-moves, with selective search explained briefly; [Stockfish's depth documentation](https://official-stockfish.github.io/docs/stockfish-wiki/Stockfish-FAQ.html#what-is-depth) makes both qualifications.
- P3 | `src/drill/drill.ts:219` | Changing Opponent rating while Maia is pending labels the returned probabilities with the new rating even though inference used the old rating. A deferred probe queried 1000 and emitted 1800. Capture the rating before the await and use that same value in the result event; apply changed ratings to subsequent requests.
